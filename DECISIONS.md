# Decisions

One line each: decision — reason. "(proposed)" = owner may veto at approval.

- D-01 Stack: Next.js App Router + TypeScript, Supabase Postgres + Auth, Vitest, Playwright, Vercel — the default stack; no change needed.
- D-02 Club time zone `America/New_York` — owner answer Q2.
- D-03 RSVP cutoff = kickoff − 2 h, closed at exactly the cutoff — owner answer Q3; one function in TS and SQL with a parity test.
- D-04 Instants stored as UTC `timestamptz`, shown in club zone with label — avoids DST bugs.
- D-05 Demo match seeded relative to now (`--demo-cutoff-in`) — class date undecided (Q3).
- D-06 Database tests on embedded Postgres 17 (`embedded-postgres`) + `auth` stub + smoke run on real Supabase — Docker not installed; owner chose Option A (Q10). Every install needs the owner's yes.
- D-07 Base tables in schema `core`, only views/functions in `public` — Supabase exposes `public` over REST; nothing sensitive may be reachable there.
- D-08 The app queries as role `anon`/`authenticated` via `pg` with `SET LOCAL ROLE` + claims, never as service role at runtime — app has no more power than a player; same code path as a direct attacker.
- D-09 RSVP written only by `rpc_rsvp_set` (SECURITY DEFINER, uses `auth.uid()`, checks cutoff with database `now()`) — makes direct-API abuse impossible, not just unlikely.
- D-10 Decisions use server time; browser keeps a server-corrected clock — wrong phone clocks cannot show a false "open".
- D-11 Local/CI auth is a test-only `LocalAuth` adapter; real Supabase Auth only in preview/prod, covered by smoke tests — GoTrue needs Docker; accepted drift risk, mitigated by smoke.
- D-12 (proposed) One Supabase project `pintfc` for preview and production — Free plan allows 2 active projects and one is already paused in the org; risk: previews share production data (threat T-20). Alternative: a second project `pintfc-staging`.
- D-13 (proposed) Auth JWT lifetime set to 5 minutes in the dashboard — limits how long a revoked token could be used directly against the database; `require_player()` also checks `auth.sessions`.
- D-14 Sign-in via our own route (`POST /api/auth/sign-in`) with a fixed minimum duration — generic errors and equal timing (AC-1.1.4).
- D-15 No sign-up, reset or email flows — out of scope; no Supabase email sending needed on the Free plan.
- D-16 Seed creates the 40 users with the admin API and writes passwords only to gitignored `credentials.local.csv` — owner answer Q5; secrets never printed.
- D-17 Adults default to public-visible, minors default hidden; DB constraint blocks minor opt-in without guardian consent — AC-4.1.3/4.3.3; `guardian_consent` is owner-set only (guardians out of scope).
- D-18 RSVP allowed for any scheduled match before its cutoff, not only "the next" one — simpler and a superset; cancelled/past rejected (AC-3.3.6).
- D-19 Optional RSVP reason ≤ 140 chars, visible only to its author — owner answer Q6.
- D-20 Maybe is a separate count; visitors see no counts — owner answers Q8, Q4.
- D-21 Latest results = 5; squad shows all visible players — owner answer Q9.
- D-22 One error format `{error:{code,message,request_id}}`; unknown errors → generic `INTERNAL` — no leaks, easy to test.
- D-23 Hidden and archived players return the same 404 — prevents existence probing.
- D-24 Polling every 10 s while visible (pause when hidden) — the PDF's default; worst case ≈ 10 s + request, inside 15 s.
- D-25 Look "Sport" light with system font and tokens in screens.md — owner pick; no font download keeps phones fast; contrast verified by axe.
- D-26 Lockout/rate limiting not built — accepted risk in the PDF while data is fake.
- D-27 Public GETs are `no-store` — freshness over caching for a small app.
- D-28 Cross-site protection by SameSite=Lax cookies + JSON-only state-changing routes + Origin check — no CSRF tokens needed.
- D-29 AC-5.2 and AC-5.4 plus LIVE-1 are tracked as gates beyond the 38 — the PDF keeps them as gates.
- D-30 All 38 check texts are "derived" wording — no spec v0.3 available (Q1).
- D-12 ACCEPTED by owner (2026-11-11): one Supabase project; previews share production data; fake data only.
- D-13 ACCEPTED by owner (2026-11-11), with a condition: when the project is created, confirm the 5-minute JWT-lifetime setting is available on the Free plan BEFORE relying on it. If it is not, record the fallback here (the `auth.sessions` check in `require_player()` and `getUser()` stay as the controls). Owned by session 18.
- D-31 Plan: 19 sessions, one layer or feature each; a check is "owned" by the session that finishes ALL its tests; earlier sessions may add API-level tests tagged `[api]` for it. Tests are tagged `[db]`, `[api]`, `[unit]`, `[e2e]` after the ID so one ID can have several tests across sessions.
- D-32 Every install (npm package or tool) needs the owner's yes first (owner answer Q10); session 01 lists them in one batch for a single approval.
- D-33 Live-in-class session is 16 (AC-2.4.3, snapshot date on the mini table): tiny, visible, safe to do in front of students.
- D-34 DB tests share ONE Postgres per run: Vitest globalSetup builds a migrated template database, each test file copies it — each run leaves one ~39 MB temp folder instead of one per file (files may not be deleted). Owner approved touching `tests/helpers/db-global-setup.ts` and `vitest.db.config.ts` in session 02.
- D-35 `players.id` has no foreign key to `auth.users` — the seed creates players with fixed ids first and creates the logins after with the same ids.
- D-36 The minor opt-in rule (AC-4.3.3) is a trigger raising SQLSTATE `PF422`, not a CHECK: it depends on today's date. The column default `public_opt_in = true` cannot know the age, so the seed sets minors' value explicitly.
- D-37 The auth stub copies Supabase's default privileges for `public` on purpose; migration 0001 then revokes them, so tests prove the lock-down on a Supabase-like starting point.
- D-38 service_role gets explicit grants on `core` (not only default privileges) so it does not depend on a real project's defaults.
- D-39 ISO strings given to the time rules must carry a zone (`Z` or an offset); a bare local time is a RangeError — reading it in the device's zone is the bug the time module exists to prevent.
- D-40 The privacy scanner flags the KEYS email, phone, date_of_birth/dob/birthdate, rsvp, rsvps, answer(s), reason, attendees, attendance, going, maybe, not_going and no_answer at any depth, plus email/phone-looking values; `rsvp_open` and plain match dates such as `played_on` are allowed — a date value alone cannot be told from a birth date, so only birth-date keys are flagged.
- D-41 `can()` gives an archived player no permissions at all, not even `read_public`; `assertCan` answers visitors with UNAUTHENTICATED (401) and players with FORBIDDEN (403) — matches rules.md and keeps "who are you" and "you may not" apart.
- D-42 The logger replaces sensitive keys (body, cookies, tokens, passwords, email, phone, date of birth, reason, authorization, secrets), masks email/JWT/Bearer text inside strings and logs Errors by name only — error messages can carry connection strings or personal data.
- D-43 The poller is a timer chain, not `setInterval`: first run 10 s after start, refetch at once when the tab becomes visible, 20 s after an error, never two runs at once — keeps load low and avoids overlapping requests.
- D-44 The countdown uses whole seconds rounded down; at exactly kickoff or later it is `kickedOff` — never shows negative time.
- D-45 `uuidSchema` is `z.guid()` (any 8-4-4-4-12 hex), not strict RFC UUID — the seed uses fixed ids that are not RFC version-4 ids.
- D-46 `core.rsvp_cutoff` and `core.rsvp_is_open` are `STABLE`, not `IMMUTABLE`, and live in `core` — timestamptz arithmetic is not immutable in Postgres, and only owner roles should execute them; later views and functions call them.
- D-47 The seed refuses any database that is not on this computer unless `--allow-remote` is passed, and never prints the connection string — an accidental run against the real project must be impossible by default.
- D-48 The demo match is the NEXT match: kickoff = now + the `--demo-cutoff-in` value + 2 h, so its cutoff lands exactly that far from now; the four regular upcoming matches follow it one week apart at the same local time, the first of them cancelled — the class sees "RSVP closed" happen live and the cancelled case is present.
- D-49 Seed dates are relative to "now": past matches are 3 + 7k days back at 19:00 club time, the season spans 120 days back to 240 days ahead, and the minors are 16 y 3 m and 15 y 8 m old today — the seed stays valid whenever it is run, and past dates simply shift on each run (same ids, updated rows).
- D-50 The seed only inserts or updates, never deletes; moving the demo match is a rerun with a new `--demo-cutoff-in` — keeps the project rule against deleting and makes reruns safe.
- D-51 Seed names are invented words (14 first names × 12 surnames, 41 distinct full names) checked against a deny-list of common real names; emails are `first.last@pintfc.test` and phones `+1-555-01xx` — no real person can match, and the fake range is reserved.
- D-52 Seed id scheme `TTTTTTTT-0000-4000-8000-NNNNNNNNNNNN` (type 1 player, 2 team, 3 venue, 4 season, 5 competition, 6 match, 7 training, 8 snapshot; matches 1..12 past, 100 demo, 101..104 regular upcoming) — deterministic valid UUIDs so reruns update rows and session 05 can create logins with the same player ids.
- D-53 The seed's `.mjs` files have no type declarations; tests import them with a typed `import * as` and a `@ts-expect-error TS7016` comment — avoids adding a `.d.ts` file outside the session's file list while keeping `typecheck` strict.
- D-54 Auth sits behind an `AuthPort` interface (`signIn`, `getUser`, `signOut`, `signOutAll`); LocalAuth is a test-only adapter and `getAuth()` refuses it whenever `VERCEL_ENV` is set (even with no `AUTH_ADAPTER`), checked on every call â€” a stand-in must never be able to reach production.
- D-55 LocalAuth keeps users and scrypt hashes in schema `local_auth` (created on first use, outside `core` and `public`) and sessions in `auth.sessions` â€” the same table the real Supabase project has, so `core.require_player()` is exercised identically.
- D-56 The session cookie is `pf_session`: one HS256 token (8 hours), `HttpOnly; SameSite=Lax; Path=/`, not `Secure` (LocalAuth runs on plain http), verified against the live session row on every request â€” so sign-out and revocation take effect at once.
- D-57 Every sign-in outcome, including a validation error, takes at least 400 ms (`SIGN_IN_MIN_MS`), and an unknown email still pays for a password hash â€” equal answer and equal timing for wrong password, unknown email and archived player, so accounts cannot be probed.
- D-58 `withApi` for POST/PUT/PATCH/DELETE: an `Origin` different from the site's own, or `Sec-Fetch-Site` marking the request cross-site, is FORBIDDEN (403); a body or content-type that is not `application/json` is VALIDATION (400); a request with no `Origin` at all (a non-browser client) is allowed because CSRF needs a browser; bodies are limited to 8192 bytes and refused as VALIDATION since 413 is not in the closed code list.
- D-59 `core.require_player()` raises the single SQLSTATE `PF401` for every failure, including a `sub` or `session_id` that is not a uuid â€” the API never has to guess between error kinds and no malformed token can surface a different error.
- D-60 Seed logins are opt-in (`--logins`), create only the missing ones, append passwords to `credentials.local.csv` (gitignored, never printed, never overwritten) and refuse `--allow-remote` â€” re-running the seed to move the demo match must never reset a student's password, and LocalAuth tables must never reach the real project.
- D-61 Password hashing and the `local_auth` schema live in one plain-JS module, `src/server/auth/local-store.mjs`, used by both LocalAuth and the seed script â€” the two can never disagree on the hash format.
- D-62 The e2e server (`tests/helpers/e2e-server.mjs`) starts its own throwaway Postgres, applies the migrations, seeds, creates logins for players 1, 2, 3 and 41 and runs LocalAuth; passwords go only to `%TEMP%\pintfc-e2e-logins.json` (never printed) and the temp folders are left behind.
- D-63 The layout reads the session on the server for every page (`force-dynamic`), so the header never flickers and never trusts the browser; every page is `no-store`.
- D-64 `src/middleware.ts` only does the cheap cookie-present check; the page itself checks that the session is alive (so a revoked cookie is refused too). Next 16 calls this file "proxy" and warns that `middleware` is deprecated; the plan names `middleware.ts`, so it was kept. Renaming later is a one-line change.
- D-65 Sign-in and sign-out finish with a full page load to `/` (never a client-side navigation), and sign-in never reads `next=`/`redirect=` (T-19).
- D-66 The sign-in form shows one message, "Email or password is incorrect", for every 4xx; 5xx and network failure show "Something went wrong. Try again."
- D-67 The settings stub shows the player's display name (`private-name`) instead of the email, because `public.rpc_me()` does not return the email.
- D-68 `public.v_next_match` computes the cutoff and `rsvp_open` inline (kickoff minus 2 h; scheduled and now before the cutoff) instead of calling `core.rsvp_cutoff` / `core.rsvp_is_open`: Postgres checks EXECUTE on functions inside a view against the caller, and `core.*` is closed to visitors on purpose. The parity test NEXT-MATCH-4 keeps the view and the core functions identical.
- D-69 The view carries `rsvp_open` and `server_now` (the database clock) so the API never computes either; the match stays "next" after the cutoff (chip says "RSVP closed") until kickoff, then it is no longer returned.
- D-70 The home next-match card is a client component that fetches `/api/home` on mount, so it has its own loading, error (retry, never raw text) and empty states; the page stays a server page with the h1.
- D-71 The countdown and the RSVP chip use `createServerClock(server_now)`, taken once per response; a new response (retry) makes a new card with a new offset. The chip is open only if the server said open AND the corrected clock is strictly before the cutoff (at the cutoff: closed).
- D-72 e2e tests freeze time with `page.clock.install` + `pauseAt` (device clock deliberately 4 h wrong) and answer `/api/home` with `page.route`, so they never depend on the shared e2e database or on how long the run has been going; only AC-2.1.1 uses the real seeded demo match.
- D-73 `v_season_record` covers the current season only (`seasons.is_current`), league competitions only, published results on `played` matches only; with nothing to count it returns NO row, so the API sends `record: null` and the page says "No results yet" (never a row of zeros).
- D-74 `v_latest_results` has no limit and no season filter; it is ordered newest match first and carries `played_at` (kickoff instant) for ordering and `played_on` (calendar date in the club zone) for display. The API orders explicitly (`played_at desc, match_id`) and takes 5 (`LATEST_RESULTS_LIMIT`), so the page never relies on the view's own ordering.
- D-75 A result row counts only when its match is `played`, even if `published` is true: a cancelled or not-yet-played match with a result row must never leak (T-11).
- D-76 `played_on` goes through the API as text ("YYYY-MM-DD", `played_on::text`) and the page formats it as a plain date (UTC, no shift), so a viewer's time zone can never move the day.
- D-77 `SeasonRecord` and `LatestResults` each fetch `/api/home` themselves (3 requests per page load together with `NextMatch`) so each section has independent loading, empty and error states; their retry buttons have their own test ids (`season-record-retry`, `results-retry`) so they never clash with the next-match `retry-button`. A shared loader would remove the extra requests but needs a new file; left for a later session.
- D-78 The new sections use inline styles only: `src/app/globals.css` was not on this session's file list.
- D-79 `v_standings` is the latest snapshot (newest `taken_on`, then `id`) of the CURRENT season; a snapshot of another season never shows even if its date is newer; no snapshot for the current season means no rows, so the API sends `standings: null` and the page says "No table yet".
- D-80 `goal_difference` is computed in the view (`goals_for - goals_against`), not stored; `won/drawn/lost`, `goals_for/goals_against` are not exposed (the mini table does not need them).
- D-81 `standings.taken_on` is in the `/api/home` response ("YYYY-MM-DD" text, as in `docs/design/api.md`) but the home page does not show it: session 16 adds `table-snapshot-date` with the owner (AC-2.4.3).
- D-82 Our row's test id is `table-row-us` and the other rows' is `table-row` (never both on one element). The highlight is a bold `table-us-label` AND a 6 px left border on the row (a border survives high-contrast / forced-colors modes), plus a light background; the other rows have no border.
- D-83 `MiniTable` is a real `<table>` (`table-layout: fixed`, columns Pos, Team, P, GD, Pts) with long team names wrapping, so it fits 320 px with no sideways scroll; it fetches `/api/home` itself (now 4 requests per page load with the other sections; a shared loader remains a later cleanup) and its retry button is `table-retry`.
- D-84 `core.is_publicly_visible(core.players)` is the single copy of the visibility rule. Because Postgres checks EXECUTE on functions used inside a view against the CALLER, it is granted to anon and authenticated, and it is the ONLY core function that is. Safe because it is SECURITY DEFINER with a fixed empty `search_path`, reads only its argument and no table (it calls only the pure date helper `core.is_minor`), `core` is not exposed through the REST API, and a caller can only pass a row it could already read (none). Guarded by VIS-FN-2 (shape and grants), VIS-FN-3 (no other core function open, checked over every function in the schema) and `CORE_FUNCTIONS_OPEN_TO_VIEWS` in the matrix (exactly one name).
- D-85 The rule does not rely on the `players_guard` trigger: a minor who is opted in without guardian consent (impossible while the trigger is on) is still hidden, and a test builds that state with the trigger disabled.
- D-86 `v_squad` and `v_player_profile` expose only name, position, shirt number and the three consent-gated optional parts; never email, phone, date of birth or any consent flag. Each optional column is NULL unless its flag is on; the API omits null keys, so the key is ABSENT from the response and the DOM, not null.
- D-87 Stats (`appearances, goals, assists, minutes`) count only published results of played matches (same rule as the home page, T-11); a player who consented to stats but has played nothing shows zeros.
- D-88 Hidden, archived, unknown and not-a-uuid ids are one outcome: `getPlayerProfile` returns `null`, the API answers one 404 body (`NOT_FOUND`, "Not found.") for all, and the page answers one 404 page; only the API distinguishes a malformed id (400 `VALIDATION`), because a malformed id reveals nothing about any player.
- D-89 The profile's 404 status is decided in `players/[id]/layout.tsx`, not only in the page: a page with `loading.tsx` is streamed and its status is already 200 by the time `notFound()` runs; a layout sits outside the loading boundary. `data.ts` wraps the lookup in React `cache()` so layout and page share one query; `players/not-found.tsx` re-exports `[id]/not-found.tsx` because a `notFound()` from a layout is caught one level up.
- D-90 The squad and profile pages are server components calling the same functions as the routes ("pages vs API", docs/design/api.md), with `loading.tsx` and `error.tsx` (retry button) per route instead of client-side fetching.
- D-91 The settings functions take no player id and the update function has parameters for the four flags only: there is nothing to point at another player, and status, guardian consent, shirt number, name, email and date of birth cannot even be named (T-06, AC-4.3.4). Enforced by the database; the API's strict body is a convenience.
- D-92 NULL means "leave this flag"; a call with no flag is `22023` (the API turns that into a 400 before it gets there). A rejected call (PF422) changes nothing, including flags sent with it.
- D-93 `PUT /api/me/settings` returns the same `{ settings }` DTO as `GET`, so the page and the tests read the saved state from the response.
- D-94 The page saves each toggle on change (no Save button), shows the change at once and puts it back on failure.
- D-95 (owner-accepted) `/settings` does NOT show `sign-out-button` / `sign-out-all-button` although `docs/design/screens.md` lists them: the header's account menu already has both, and a second copy would need its own tests. The screen design is not updated here.
- D-96 (owner-accepted) The function's own minor check is kept alongside the `players_guard` trigger (defence in depth) and is tested on its own with the trigger switched off.
- D-97 The privacy sweep discovers public objects from the catalog (`pg_class`, `pg_proc`) instead of a hand-kept list, and inventory tests (`API-INVENTORY`, `PAGE-INVENTORY`) fail when a route or page file exists that the sweep does not know about, so a new public surface cannot slip in unscanned.
- D-98 A public response is clean only if BOTH checks pass: `assertNoPii` (keys, email/phone-looking values) and "none of the seeded private values appears". The second check does not depend on the scanner's patterns, so a renamed key (`organiser`, `born`) cannot hide a leak.
- D-99 Any public key or column whose name looks like RSVP data (`rsvp|attend|going|maybe|answer|reason|respon`) fails T-12, except `rsvp_open` (a flag about the match).
